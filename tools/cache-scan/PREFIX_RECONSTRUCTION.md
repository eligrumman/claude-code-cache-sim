# Can we reconstruct a live session's prompt prefix to warm its cache externally?

**Verdict: NOT VIABLE for external replay against a live session's real cache entry.**
Viable only in the degenerate sense of "reconstruct *a* prefix that's a strict
subset/near-miss of the real one" — which is exactly what does NOT hit the
same cache entry, since Anthropic's prompt cache is keyed on an exact content
hash of the prefix up to the `cache_control` breakpoint. One differing byte
anywhere before the breakpoint (system prompt, tool schema ordering, an
injected reminder, thinking signature, a truncation marker) is a full cache
MISS, not a partial hit.

## What was checked

Investigated two real transcripts:
- `~/.claude/projects/-Users-user-investor/ef5d93fc-fd61-4ed2-a723-edff640ece7b.jsonl` (27,636 records, 8,850 API turns)
- Binary string scan of `/Users/user/.local/share/claude/versions/2.1.239`

### 1. Message history — mostly recoverable, with caveats
JSONL records of `type: "user"` / `type: "assistant"` (excluding `isSidechain`)
carry `message.content` in the real Anthropic API content-block shape: text,
`thinking` (with opaque `signature`), `tool_use`, `tool_result`. This is not
a reformatted summary — it looks like the literal blocks that were sent to /
received from the API. The prototype recovered 8,850 messages / 8,851 blocks,
349 signed thinking blocks, 3,165 tool_use/tool_result pairs.

Caveats that still break byte-identity:
- `tool_result` content for non-text/large outputs may be truncated or
  normalized by the CLI in a way that isn't guaranteed to match a fresh
  reconstruction exactly (truncation markers, image encoding).
- Sub-agent turns live in separate `<session>/subagents/*.jsonl` files
  (`isSidechain: true` in the parent stream); how/whether the harness folds
  their output into the parent thread's cached prefix is not observable from
  the parent transcript alone.

### 2. System prompt — NOT recoverable byte-exact
Never appears in JSONL. Binary string scan of the `claude` executable
confirms a system-prompt **template** is compiled in (`"You are Claude Code"`,
`<env>`, `"Today's date is"`, a `gitStatus` block) but populated with runtime
values (date, cwd, git branch/status, permission mode, model id, plugin/skill
listing) at process start / per turn. This can only be regenerated by
literally running the same CLI build's prompt-assembly logic with matching
runtime state — not from the transcript.

### 3. Tool definitions — NOT recoverable
Transcript records only `tool_use` **calls** (name + the input actually
passed), never the registered name/description/JSON-schema for the full tool
set offered every turn. The complete tool list (built-ins + whichever MCP
servers happen to be connected at that process's startup) is assembled by
the running CLI/MCP handshake and isn't logged anywhere in JSONL.

### 4. Dynamic / volatile content
Confirmed sources of run-to-run drift: timestamps, cwd, git status,
MCP server availability, `<system-reminder>` injections (skills list, deferred
tool list, date-change notices — some inlined into recorded `user` turns,
others generated fresh for the *next*, not-yet-existing turn), thinking-block
signatures, request-level metadata (beta headers, service tier) not stored
per-message at all.

### 5. Cache breakpoint location — implies the WHOLE conversation must match
`usage.cache_creation_input_tokens` on resume turns runs 45k+ tokens (per the
sampled transcript; the broader scan data cited 60k–160k), far larger than a
static system+tools head. That means Claude Code's `cache_control` breakpoint
sits near the tail of the growing conversation — it is caching the entire
accumulated prefix, not just a fixed head. So the reconstruction bar isn't
"get the boilerplate right," it's "reproduce the ENTIRE conversation history
plus system prompt plus tools, byte-for-byte, as of the live process's
in-memory state" — including whatever that process does internally before
sending (e.g., any request-time normalization) that the JSONL never records.

## Prototype

`tools/cache-scan/prefix_probe.py` — read-only. Takes a session JSONL path,
walks the main-chain (non-sidechain) `user`/`assistant` records, reconstructs
an Anthropic-shaped `messages` array, and prints:
- messages/blocks recovered (with thinking-signature / tool_use / tool_result
  breakdowns)
- a rough token estimate (chars / 4)
- the same explicit gap list summarized above

It performs no network calls. Example run (read-only, against a real 27k-record
transcript):

```
API messages recovered (user+assistant, main chain): 8850
Content blocks recovered: 8851
  thinking blocks WITH signature:    349
  thinking blocks WITHOUT signature: 0
  tool_use blocks:                   3165
  tool_result blocks:                3165
Rough token estimate (chars/4): 1,275,946 tokens
```

## Bottom line

- The **message-history bytes** are largely present and structurally correct
  in JSONL — this is the one piece that's genuinely recoverable.
- The **system prompt and tool definitions are not in the transcript at all**
  and are runtime-assembled by the CLI binary with per-run dynamic values —
  no way to regenerate them byte-exact from outside the running process.
- Because Claude Code's cache breakpoint covers the full conversation (not
  just a static head), even a perfect message-history reconstruction is
  insufficient — the missing system-prompt/tool-defs prefix that precedes it
  in the hashed bytes guarantees a mismatch, and a mismatch anywhere before
  the breakpoint is a full miss of the whole cached blob, not a partial hit.
- A `max_tokens: 0` warm call built from an externally reconstructed prefix
  would therefore write a *new*, different cache entry — paying full
  cache-write cost for a prefix the real live session can never reuse either.
  Net effect: pure waste, not a warm-up.
- **The only real path to warming a live session's actual cache entry is
  from inside Claude Code's own process/harness** (a hook that fires with
  access to the exact in-memory request the CLI is about to send, or a
  first-party feature) — not external transcript replay.
